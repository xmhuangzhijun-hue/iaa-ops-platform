# 容量假设与压测验收

「高并发」必须先变成数字，否则无法验收。以下是**待验证的假设**，不是已测得的结论。

## 1. 容量假设

| 项 | 假设值 | 说明 |
|---|---|---|
| 租户数 | 5 | 公司 + 代理 |
| 同时在线用户 | 30，峰值 60 | 投手与运营白天在线 |
| 媒体账户数 | 500 | 跨 5 个平台 |
| 推广（计划）数 | 20,000 | 其中在投约 6,000 |
| 投放事实日增 | 6,000 × 24 ≈ 144,000 行/天 | 按小时粒度 |
| 变现事实日增 | 约 300,000 行/天 | 来源包粒度更细 |
| 回传事件 | 约 200,000 次/天，峰值 20 次/秒 | 有时效性 |
| 事实表保留 | 25 个月（同比需要去年同期） | 事件表保留 3 个月 |
| 在线报表目标 | 30 天范围 p95 < 1.5s，90 天 p95 < 4s | 到达不了再谈分析库 |
| 采集延迟目标 | 当日数据延迟 < 15 分钟 | 回传链路 < 2 分钟 |

按上表，事实表两年约一亿行级别。PostgreSQL 配合按月分区与合适索引应可承载；这是待验证结论，不是保证。

## 2. 压测场景（不测单接口）

真正要测的是混合负载：**有人在查报表，同时定时采集在跑、有人在导出历史、另一个人在批量改规则。** 用 k6 组合场景：

| 场景 | 配比 | 断言 |
|---|---|---|
| 聚合查询（7/30 天，随机维度组合） | 50% | p95 达标，结果正确 |
| 推广列表翻页与排序 | 20% | p95 < 1s |
| 采集写入（模拟上游持续入库） | 持续 | 不阻塞在线查询 |
| 导出（10 万行） | 5% | 异步返回任务，不占用在线连接池 |
| 批量改规则 / 批量回传 | 5% | 写入正确，审计完整 |
| 越权请求 | 5% | 全部被拒，且不泄露存在性 |

## 3. 验收指标

1. 上述混合负载持续 30 分钟，在线查询 p95 不超过目标值的 1.5 倍。
2. 错误率 < 0.1%，且没有一条是因为权限判定被绕过。
3. 采集与导出运行期间，在线查询不出现连接池耗尽。
4. 压测后数据校验：事实表合计与压测注入量一致，无重复计数、无丢失。
5. 数据库恢复演练：从持续归档恢复到指定时间点，校验事实行数与校验和。

## 4. 不做的事

- 不用「返回固定 JSON 的接口」测吞吐量，那测的是框架不是系统。
- 不用功能验证用的 51,840 行数据宣称承载能力。
- 不在没有压测结论前引入 ClickHouse 或 Kubernetes。
