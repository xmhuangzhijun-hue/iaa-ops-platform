# ADR-0004 后端技术栈与演进路线

- 状态：已采纳（2026-09-16）
- 取代：ADR-0001 中「后端用 FastAPI」的部分；前端组件库见 ADR-0003，契约先行原则继续有效
- 前置：ADR-0002、ADR-0003

本文同时保留目标路线与逐阶段实施记录。当前实际运行的是 React 前端、Java 模块化单体和 PostgreSQL；Python 只用于契约模型、演示种子和迁移对照。独立采集 Worker、媒体 API 接入、Redis、消息队列和 ClickHouse 均未实现或接入。当前交付清单以 [README](../../README.md) 为准。

## 背景

界面已把数据与交互需求压出来：多平台采集、变现归因、回传闭环、多维聚合、多租户与四层权限、财务结算。项目要开源并作为工程能力证明，选型需兼顾业务复杂度的组织方式与招聘面。

## 决策

| 层 | 选型 | 职责 |
|---|---|---|
| 主业务后端 | **Java 21 LTS + Spring Boot 4.1**（已实现） | 当前承载认证权限、账户分配、报表、导出、审计与 Excel 导入；其余档案、推广配置和规则为规划 |
| 认证授权 | Spring Security + 自建业务授权模型 | 认证与接口鉴权；数据范围与字段可见性由业务模型实现 |
| 主数据库 | **PostgreSQL 17** | 档案、配置版本、事实表、任务状态、审计 |
| 缓存 | Redis（按需引入） | 热点字典缓存、限流计数、幂等键，不作为唯一事实存储 |
| 异步任务 | RabbitMQ + 独立 Worker（按需引入） | 采集、补数、批量回传、导出、通知 |
| 采集与清洗 | Python Worker（未来规划，未实现） | 待媒体接入需求明确后实现 API 适配、字段映射与清洗，写入 staging；当前 Python 仅为契约、种子和对照工具 |
| 大规模分析 | ClickHouse（有门槛才引入） | 跨平台、长周期、多维聚合报表 |
| 架构形态 | Java 模块化单体（已实现）；独立 Worker（未来规划） | 先划清模块边界，按真实任务需求和负载再决定是否拆分部署 |

### 版本选择

项目固定使用 **Java 21** 工具链与 **Spring Boot 4.1.1**，构建依赖见 `backend-java/build.gradle.kts`。选择以本项目已完成的编译、集成测试和运行验证为依据；升级 Java 或 Spring Boot 时重新执行这些验证，确认兼容性。

## 三个必须先定死的前提

### 1. 指标口径只能有一份实现

这是本项目的立身之本：页面、合计、导出、异常判定共用一套派生指标。当前权威实现位于 Java `shared/metrics`，由 `reporting` 使用；Python 保留迁移前实现用于对照，修改口径时同步两侧。未来采集 Worker 只允许写入基础指标（消耗、曝光、点击、启动、回传、转化、各类收益金额），不另行计算派生指标。

运行组件各自计算 ROI / CPC / ARPU，容易在小数处理、空分母和汇总顺序上分叉，因此对外业务统一使用 Java 的指标实现。数据范围与字段可见性也由 Java 业务入口强制；未来 Python Worker 不对外提供业务查询接口。

### 2. 现有 FastAPI 后端的去向

决策时状态：认证、数据范围、指标口径、六个看盘接口与导出已实现，44 项测试通过，契约由代码导出。后续迁移结果见本文实施记录及 [项目状态](../STATUS.md)。

处置方式：
- 契约不变。因为一直是契约先行，前端不关心由谁实现；`contracts/openapi.json` 与既有契约测试直接成为 Java 实现的验收基准。
- Java 逐模块接管业务入口后，Python 保留契约模型、演示种子和迁移对照。未来可在独立采集需求出现时复用其基础工具；当前没有已实现的平台 API 接入或采集 Worker。
- 过渡期间两边同时可运行，但同一接口只由一侧对外提供，避免出现两个事实来源。

### 3. 组件分期引入，不一次堆齐

单人维护、开发机可用内存常在 1–3 GB。引入顺序与条件：

| 组件 | 引入条件 |
|---|---|
| PostgreSQL | 立即，已在用 |
| RabbitMQ | 开始做采集调度或批量回传时 |
| Redis | 出现真实热点或需要限流 / 幂等键存储时 |
| ClickHouse | 索引、查询优化与必要预聚合做完后，报表仍达不到响应目标，或报表明显影响业务写入 |
| Kubernetes | 需要多副本独立扩缩容时；本机开发不引入 |

「60 天、51,840 行」只能证明功能可用，不能证明承载能力，也不构成引入分析库的依据。

## 代价

- 双语言：当前需要维护 Java 业务服务与 Python 契约、种子、对照工具两套构建和依赖。未来若引入 Python 采集 Worker，应将职责限制为「从平台 API 取原始数据 → 落 staging」，并以实际接入需求说明新增运行组件的成本。
- 迁移期：Java 达到现有六个看盘接口的同等能力前，功能不新增，只搬迁与补测。
- JVM 常驻内存高于当前 Python 服务，本机开发需预留。

## 实施记录 · iam 模块（2026-09-17）

第一个切片是 `iam`：登录、令牌轮换、临时口令、权限与数据范围、界面偏好，外加 `/health` 与 `/metrics`。实现过程中确认或修正了几件事，记在这里避免后来者重走：

- **Spring Boot 4 的包重排要当成迁移成本估进去。** Jackson 3 的 databind 在 `tools.jackson.databind`（注解仍在 `com.fasterxml.jackson.annotation`）；MockMvc 的测试支撑从 `spring-boot-starter-test` 拆到 `spring-boot-starter-webmvc-test`，注解落在 `org.springframework.boot.webmvc.test.autoconfigure`。教程与既有答案多数还停在 Boot 3，按旧包名写必然编译不过。
- **Testcontainers 必须跟 Boot 对齐到 2.0.5。** 1.20.4 的 docker-java 默认协商的 API 版本低于 Docker Desktop 的 `MinAPIVersion=1.44`，表现是 `/info` 返回 400、报「Could not find a valid Docker environment」，很容易误判成本机没装 Docker。2.x 的坐标也改名为 `testcontainers-<module>`。
- **认证装配属于 `iam`，不放共享内核。** `SecurityConfig` 一度放在 `shared/config` 并注入 `iam` 的过滤器，形成共享内核反向依赖业务模块。已移入 `iam/security`，并由 ArchUnit 规则「共享内核不依赖业务模块」持续拦截。
- **重放检测不能被事务回滚吃掉。** 刷新令牌重放时要「吊销该账号全部刷新令牌」再返回 401，但 `@Transactional` 默认遇 `RuntimeException` 回滚，吊销会跟着回滚、泄露的令牌继续可用。改为 `@Transactional(noRollbackFor = ApiException.class)`，并给取令牌加 `PESSIMISTIC_WRITE` 行锁（对齐既有实现的 `with_for_update`）。这个缺陷是集成测试发现的，不是评审发现的。
- **字段名的大小写风格在边界上转换。** 契约一律 snake_case，Java 侧保持驼峰，由 `spring.jackson.property-naming-strategy: SNAKE_CASE` 统一转换；校验错误里的字段名也转成 snake_case，与请求体一致。

### 验收：与既有实现逐字段对照

两个服务连同一个库，同一批请求对照响应：53 项中 51 项完全一致，2 项是**有意的差异**——

| 场景 | 既有实现 | Java 实现 | 取舍 |
|---|---|---|---|
| 未带令牌访问不存在的路径 | 404 `NOT_FOUND` | 401 `AUTH_REQUIRED` | 先鉴权再路由，不向未认证方泄露路径是否存在；带令牌时两侧同为 404 `NOT_FOUND` |

令牌轮换与重放另做了一次对照：轮换 200、重放 401、重放后新令牌同样作废，两侧一致。

`ddl-auto: validate` 仍指向 Alembic 管理的真实库——Java 侧实体与既有表结构一致，是启动即校验的；集成测试用 Hibernate 建表只为隔离运行，不作为表结构真值。

## 实施记录 · reporting 模块与对照工具（2026-09-17）

第二个切片是 `reporting`：筛选可选值、聚合、分天、趋势、ROI 异常、原始明细与 CSV 导出。至此 Java 侧覆盖契约里的全部 24 个操作（含 8 个按契约返回 `501` 的系统管理接口），前端开发代理默认切到 Java。

- **对照从一次性脚本变成仓库里的工具。** `tools/parity/check.py` 用声明式用例表描述请求，把同一批请求打到两个服务上逐字段比较，有意差异写在 `KNOWN_DIFFS` 里并带原因，其余差异一律失败退出。上一轮的对照是临时脚本，迁 reporting 前先把它固化下来——否则每搬一个模块就要重写一次比对逻辑，而且无法回归。59 个用例目前零失败。
- **口径要逐位可比，精度与舍入必须一起对齐。** 派生指标的除法原本用 `MathContext(16, HALF_UP)`，而既有实现是 Python `Decimal` 默认上下文（28 位有效数字、HALF_EVEN）。展示层取整同样是 HALF_EVEN。不对齐的话大部分数字看着一样，只在边界上偶尔差一个末位——这种差异最难在验收时发现。
- **维度枚举同时当 SQL 列名白名单。** 分组、排序、关键词匹配的列都从 `Dimension` 枚举取，请求里的字符串永远不拼进 SQL；未知维度直接 422。动态 SQL 的注入面就此关掉，不依赖"记得转义"。
- **事实表与映射表补了只读实体。** 查询走 JdbcTemplate 的 SQL，但仍为两张表写了 JPA 实体，目的有二：启动时 `ddl-auto: validate` 会校验 Java 用到的列与 Alembic 建的表一致；集成测试按同一份定义建表。实体本身不参与读写。
- **待实现的接口答 501 而不是 404。** 路径是契约的一部分，"还没做"与"不存在"对调用方是两件事。这里与既有实现有一处有意差异：FastAPI 会先跑请求体校验，带错请求体时返回 422；Java 直接答 501——不去校验一个根本不会被处理的请求体。

### 两侧对照的边界

对照脚本比的是「同一个库、同一批请求下的响应」，因此它证明不了：并发行为、性能、以及两边都没覆盖到的输入。已知未覆盖的一类：请求体和权限同时不成立时，FastAPI 先解依赖返回 403，Spring 先做请求体校验返回 422。用例里没有这种叠加错误，真要统一得把权限判断前移到过滤器。

## 实施记录 · 系统管理三件套与表结构改由 Flyway 管（2026-09-17）

第三个切片是第 3 阶段的系统管理功能，直接写在 Java 侧：映射管理（`mapping`）、用户与权限（`iam` 的账号管理）、审计日志（`governance`）。契约里只剩数据导入还返回 `501`。

### 表结构的管辖权从 Alembic 移到 Flyway

前两个切片里 Java 只读既有表，所以 schema 一直归 Alembic 管，Java 用 `ddl-auto: validate` 校验。这一轮要建新表（`audit_events`、`import_tasks`），继续让 Python 侧建 Java 要用的表就说不通了——写功能的人和改表的人得是同一边。

- `V1__core.sql` 是 Alembic `0001_core` 的逐字转写，`V2__audit_and_imports.sql` 新增审计与导入任务两张表。
- 已有的库（本机、CI）靠 `baseline-on-migrate: true` + `baseline-version: 1` 打基线：V1 视为已应用、不重跑，只跑 V2；新库从 V1 从头建。本机实测就是这条路径——Flyway 在 Alembic 建出的库上打了基线，然后只应用了 V2。
- Python 侧的 Alembic 迁移**就此冻结**，不再新增版本。两套迁移工具同时能改一个库是危险的，这里靠"只有 Flyway 往前走"这条约定挡着，没有机制强制。
- `ddl-auto` 仍是 `validate`：迁移建表、实体校验，两边对不上就启动失败。集成测试也改成跑同一份迁移再 validate——测试自己建表的话，迁移写错了测试反而发现不了。

**Boot 4 的坑（第二次踩同类）**：只加 `org.flywaydb:flyway-core` 不会触发自动迁移，Boot 4 把各技术的自动配置拆成了独立模块，要的是 `spring-boot-starter-flyway`。症状是启动日志里一行 Flyway 都没有、然后 Hibernate 报 `missing table`，很容易误判成迁移脚本写错。

### 对照工具随之升级：基准落后的接口改由契约当裁判

映射、账号、审计这三个接口只有 Java 实现，FastAPI 仍答 501——"逐字段比两侧"在这里失去意义。工具因此分成两种判法：

- 有基准的接口：照旧逐字段对照；
- 超出基准的接口（`beyond=True`）：断言"既有实现 501、Java 2xx"，响应结构改由 `contracts/openapi.json` 校验。

顺带把契约校验加到了**所有** Java 的 JSON 响应上（`tools/parity/contract.py`，只实现契约里真正用到的那部分 JSON Schema）。校验器本身用五种错法自证过：缺必填字段、类型不符、多出契约没有的字段、枚举越界、const 不符——都能报出来，不是"零命中所以通过"。

### 两个 Postgres / JPA 上的坑

- **`(:param is null or col = :param)` 在 Postgres 上会炸**：参数只出现在 `is null` 里时推不出类型，报 `could not determine data type of parameter`；把关键词拼进 `concat` 时还会被当成 `bytea`。解法是在 JPQL 里显式 `cast(:param as String)`，包括 `concat` 里的那一处。
- **`@Modifying(clearAutomatically = true)` 会把实体变成游离对象**：改角色时先做批量删除再改用户行，范围与版本号的修改根本不会落库，接口却照常返回 200——单测里"改完再用旧版本号改一次应当 409"才把它抓出来。改成先改用户行、再重写角色。

这两条都是"接口看着正常、数据没落地"的类型，评审时几乎看不出来，只能靠断言到数据层的测试。

## 实施记录 · 数据导入与契约清零（2026-09-17）

最后一个切片是 Excel 兜底导入（`ingestion`）。契约里的 24 个操作至此全部由 Java 实现，`501` 清零。

- **按天整体替换，而不是按行去重。** 文件覆盖了哪几天，就把这几天在该媒体下的既有行全删再写入。重复导入同一天不累加，也不需要在行级别维护幂等键——媒体导出表本来就没有稳定的行标识。替换与任务状态在同一个事务里，失败就整批不落地。
- **受理与处理分开。** 上传只做三件事：记任务、留痕、把内容交给后台线程，随即返回 `202`。解析放在请求线程里，文件一大请求就挂着，前端也拿不到进度。任务状态 `pending → processing → succeeded / failed`，处理线程里的异常必须自己落成 `failed`，否则任务会永远停在 `processing`。
- **提交后再派活。** 后台处理在事务的 `afterCommit` 里触发：先派活的话，后台线程可能读到还没落库的任务。
- **坏行只跳过坏行。** 单行解析失败记下行号与列名继续往下走；一行都没解析成功才判整份失败。错误只留前 20 条——前几条足够定位问题，全量堆进任务记录只会把库撑大。
- **报给用户的是表头上的列名。** 缺列时提示「缺少必需的列：日期」而不是内部字段名 `stat_date`。这条是测试断言逼出来的，写的时候两者都"能跑"。
- **表头按别名认列。** 各家媒体导出表的列名不统一（消耗 / 花费 / 成本 / cost），认得的取值、认不得的忽略；必需列只有日期、账户、消耗三项。

### 一个没拆干净的边界

`ad_facts` 现在是**读在 `reporting`、写在 `ingestion`**，两个模块各有各的 SQL。`module-boundaries.md` 原本设计了独立的 `facts` 模块承担这张表的读写，现在没有拆出来。

不拆的理由是拆它要动已经跑通并做过逐字段对照的查询代码，而当前只有两个调用方、方向清晰（ingestion 写、reporting 读）。触发拆分的条件写在这里：**第三个模块需要动 `ad_facts`，或者归因作业（`revenue_attributed`）落地时**——那时候读写口径会开始分叉，必须有一个地方统一。

## 实施记录 · 登录失败限流与锁定（2026-09-17）

当前仍是单实例演示，采用 JDK 内存计数，不为这一项功能新增 Redis。`iam/LoginProtection` 只负责短临界区内的账号/IP 原子预占和失败状态，口令哈希和数据库调用在锁外执行。它不是通用限流框架；部署多实例或要求重启保留锁定时，必须换成共享、原子更新的状态存储（Redis 或数据库），不能把多份内存状态当作全局限制。

- 配置在 `app.login-protection`：账号 5 次、IP 20 次，失败窗口 15 分钟、锁定 15 分钟，每个维度最多 10,000 个记录。时间窗由首次尝试起算；第 N 次失败开始完整锁期。未到阈值时窗口到期清零；锁定期请求不会延长锁期。
- 账号键与数据库查询一致，保持大小写和空白原样；不存在、停用的账号也计数。所有认证失败和锁定都返回相同 `401 INVALID_CREDENTIALS` 与文案，不告诉调用方账号是否存在、命中了哪个维度或还剩几次。继续使用现有枚举，语义同步到 Python 契约源、`x-code-descriptions` 与生成类型；没有迁移契约导出器。
- 来源取 `HttpServletRequest.getRemoteAddr()`，显式关闭转发头解释。`X-Forwarded-For` 和 `Forwarded` 不由客户端决定限流键。**经反向代理部署时，默认所有访问会按代理地址共享 IP 限制**；公开部署前须在入口层限流，或配置只信任指定代理且禁止直连后端的地址还原方案，不能直接信任任意转发头。
- 在途校验占用额度，避免并发穿透；临时在途满额只拒绝当前请求，不开启或延长锁期。过期且没有在途请求的记录会回收，容量满时拒绝新键，不淘汰有效锁定。异常始终释放额度，数据库故障不算错口令。
- 登录和改密事务提交后清零账号及**当前来源 IP**，其他来源 IP 的失败计数不清除，避免一个账号改密给其他攻击来源解除限制。旧在途请求使用代数隔离，不能恢复清零前的失败计数。成功重置共享 IP 是明确取舍：持有合法口令的人可以重置该 IP 的失败累计，故这层不是入口总请求速率或资源耗尽防护。
- 内存状态在进程重启后丢失，多实例间不共享；IP 共用（NAT/代理）会连带影响同出口用户；账号锁定也可能被用来暂时阻止他人登录。这些是演示部署的适用边界，不宣称已完成公网抗滥用设计。
- 集成测试注入可控 `Clock`，不等真实 15 分钟。对照脚本维持原有每角色缓存令牌的流程，没有关闭或放宽默认保护。
